# Architecture and conventions

## Shape of the system

One Laravel API (a modular monolith) serves the customer website, the admin portal and the mobile app. PostgreSQL holds every record; Redis runs queues, caches and rate limits; Laravel Reverb (`apps/realtime`) pushes live campaign progress.

```
apps/web (Next.js) ──┐
apps/admin (React) ──┼──> apps/api (Laravel, /api/v1) ──> PostgreSQL
apps/mobile (Expo) ──┘                │                 ──> Redis (queues, cache)
       ▲                              ├──> Moyasar, SMS, courier APIs
       └──── apps/realtime (Reverb) <─┘ campaign progress
```

## API contract

`apps/api/openapi/v1.yaml` (OpenAPI 3.0) is the contract every client builds against. It covers the customer and admin endpoints for the whole MVP, ahead of the code:

- Each operation says which epic ships it (`x-epic`) and whether Laravel serves it yet (`x-status: live`) or only the mock server does (`x-status: mock`).
- The mock server (Prism) answers every operation from the contract, so the website and admin portal can be built before the backend. It also rejects requests that break the contract.
- In the test suite, every response from an `/api/v1` route is checked against the contract, and a coverage test fails if a route is missing from the contract, if a served route is still marked `mock`, or if a `live` operation has no route.
- An API change and its contract change go in the same pull request. When an endpoint ships, flip its `x-status` to `live` in that pull request.

## Customer website

`apps/web` is a Next.js app that renders on the server and calls the API from there, with the customer's token kept in an httpOnly cookie. The browser calls the API directly only for public reads (campaign progress polling). Types come from the contract (`npm run api:types`), and CI fails if they drift. Its browser tests run against a stateful fixture API behind Prism in proxy mode, so a request that breaks the contract fails the build. Details: [apps/web/README.md](../apps/web/README.md).

## Domain modules

Business code is grouped by domain under `apps/api/app/Modules/<Domain>`, added as each epic starts:

| Module | Owns | Epic |
| --- | --- | --- |
| Identity | customers, OTP, addresses, admin users, roles | E5 |
| Catalog | products, variants, images, categories | E6 |
| Supplier | suppliers, quotations, landed cost | E6 |
| Campaign | campaigns, participations, reservations, closing job | E7, E10 |
| Pricing | tiers, hold price, final price, margin check | E8 |
| Payments | holds, captures, voids, refunds, webhooks, reconciliation | E9, E15 |
| Orders | customer orders, invoices, supplier purchase orders | E11, E12 |
| Fulfillment | inbound receipts, shipments, tracking | E13 |
| Notifications | SMS and push messages | E14 |
| Finance | ledger, approvals | E15 |

A module may call another module's public services, never its tables directly. Shared building blocks live in `app/Support`.

## Identity and sign-in (E5)

- **Two kinds of account, kept apart.** Customers are `users`; staff are `admin_users`. Each has its own Sanctum guard (`customer`, `admin`), and a guard accepts only its own model's tokens, so a customer token is refused on admin routes and the reverse. There are no sessions or cookies: every client sends `Authorization: Bearer`.
- **Customers** sign in with a Saudi mobile number and a 6-digit SMS code. The first sign-in creates the account. Tokens last 90 days, one per device.
- **Admins** sign in with email and password, then an SMS code to their phone. Only the code step issues a token, which lasts 12 hours. Sign-ins and sign-outs are audited.
- **Codes** are stored as an HMAC bound to the challenge ID, expire after 5 minutes, and are spent after 5 wrong tries. Rate limits are in `config/groupbuy.php` under `auth`: codes per number (customers) or per admin account, whatever the IP; requests per IP; and admin password attempts per email, per email and IP, and per IP.
- **Blocking** an account stops its tokens on the next request, before they expire.
- **Roles and permissions** use spatie/laravel-permission on the `admin` guard. `App\Modules\Identity\Permissions\AdminPermissions` is the source of truth; `admin:sync-roles` writes it to the database. Each admin operation in the contract names its permission in `x-permission`, and its route checks it with `->can('<permission>')`; a contract test keeps the catalogue, the contract and the routes in step. Endpoints check permissions, never role names. `approvals.decide` (approving refunds, manual captures and voids, ledger adjustments and campaign cancellations) belongs to finance alone, not to `super_admin`, so releasing money always takes finance.
- **Admin accounts** are managed in the portal by admins with `admins.manage`. Nobody can change their own roles, status or password there, and nobody can hand out more than they hold: an admin can grant only roles whose permissions they have, and can only block (not otherwise change) an admin who holds a permission they lack. So a super admin cannot create or take over a finance account; finance admins are created and changed on the server with `admin:create` and `admin:update`. Each admin has their own phone number. Blocking an admin, resetting their password or changing their phone deletes their tokens and cancels any sign-in in progress; status changes write a status history row; every change is audited without the password.
- **Field permissions.** When one field of an operation needs more than the operation's permission (approving a campaign below the margin floor needs `campaigns.override_margin`), the contract names it in `x-field-permissions` and the controller checks it. A contract test makes sure every role holding such a permission also holds the operation's own.
- **SMS** goes through `App\Modules\Notifications\Sms\SmsSender`. The only driver so far, `log`, writes to the log and refuses to run in production, so production sign-in fails with `sms_unavailable` until a provider is configured.
- **Phone numbers** are stored in E.164. `App\Support\Phone\SaudiMobile` accepts the ways people type them (05…, 9665…, Arabic-Indic digits).

## Catalog and sourcing (E6)

- **Products** come from Alibaba listings and are sold only through campaigns. Each has variants (SKU, options such as `{"color": "black"}`, size and weight) and photos. A product starts as a draft and can go active only with an active variant; its last active variant cannot be archived while it is active. Variant changes lock the product row, so two admins cannot race past that rule.
- **Categories** nest through `parent_id`. Moves run one at a time (a transaction advisory lock) and refuse loops (`category_cycle`).
- **Suppliers** start as prospects. Editing needs `suppliers.edit`; the approval decision is a separate endpoint needing `suppliers.approve`, so the person who adds a supplier need not be the one who approves it. Only approved suppliers will back a campaign (E7).
- **Quotations** record a supplier's quote in its currency (`unit_cost_minor`, `currency`, `fx_rate_to_sar` as an exact decimal) and the landed cost per unit in halalas, broken down into product, freight, customs duty, import VAT, clearance and last mile. The server adds up the total. A quote can be accepted only while `valid_until` has not passed in Riyadh, and `quotations:expire` marks old ones expired every night. Once a campaign past draft relies on a quote it is frozen (`quotation_frozen`); `Supplier\Services\QuotationUsage` answers that, and E7 fills it in.
- **Files.** Photos are public (`groupbuy.media.disk`); quote files are private (`groupbuy.media.documents_disk`) and reach the portal as 30-minute signed links. Files are written before the database row and removed if the transaction fails; deleted rows lose their files after the commit.
- **Updates replace.** Admin `PATCH` requests for categories, products, variants, suppliers and quotations send the whole record; optional fields left out are cleared (a category's `sort_order` goes back to 0). A status left out keeps its current value. A unique value taken by another request at the same moment is answered with the same 422 as the form check (`App\Support\Database\UniqueViolation`).
- **Supplier approval follows the store.** Changing an approved supplier's store URL or country sends it back to `prospect` for a new review; a blocked supplier stays blocked.

## Campaigns, pricing and holds (E7, E8)

- **Lifecycle.** `draft` → `pending_approval` → `scheduled` → `active` → `closing`, with rejection back to `draft` and cancellation before any capture. `Campaign\Services\CampaignLifecycle` makes every change under the campaign row lock and writes a `campaign_events` row in the same transaction. That append-only table is the campaign's history (status changes, price changes, the deal confirmed, the maximum reached), so campaigns do not use `status_transitions`; participations and payments do. Admin actions are audited and bump `lock_version`. A draft edit or tier save sends the `lock_version` it read, and a stale one gets 409 `stale_campaign`. Draft edits replace, like the catalog's.
- **Approval** re-runs the submit checks (valid tiers, a landed cost, an approved supplier, a usable quote, an active product whose chosen variants are all active) and the margin check. It snapshots the landed cost, moves a start that has passed to now, and sets `deadline_at` to the start plus 7 days. From then on the terms are locked; the only change is one deadline extension, which must end at least 3 days before the earliest hold (paid or still waiting) expires.
- **The scheduler** runs `campaigns:tick` every minute: scheduled campaigns open at their start, unpaid reservations are freed after 15 minutes, and active campaigns past their deadline start closing (the closing job below takes over at `settling_joins`).
- **Tiers** (`Pricing\TierSet`) cover 1 to `max_qty` with no gaps or overlaps, and the price never rises with quantity. Each save stores a new full version; old versions stay. A join holds the price of the tier for `committed_qty + 1`. A variant archived after approval is hidden from customers and can no longer be joined. The price the customer saw is only compared: a different one is 409 `price_changed` with the current price.
- **Margin** (`Pricing\MarginCalculator`): the net price is the price without 15% VAT (rounded half up), and the margin is net price less landed cost, payment fee and delivery estimate. The fee (2.75% plus 1.00 SAR, from `config/groupbuy.php`) is worked out on the highest tier price so no tier understates it. `margin_bp` is floored, and every tier must reach 1500. Approving below that needs `campaigns.override_margin` and a reason.
- **Joins never oversell.** The campaign row is the only counter. A join reserves units with one conditional `UPDATE ... WHERE status = 'active' AND deadline_at > now AND committed_qty + reserved_qty + qty <= max_qty`. Under READ COMMITTED a waiting update re-checks that condition against the newest row, so contenders past the maximum fail at once with `sold_out`. The row lock also serializes the per-customer limit, and a CHECK constraint is the last defence. `tests/Feature/Campaign/ConcurrentJoinsTest` races real processes against it. Retrying with the same `client_request_id` returns the first join: copies sent at once wait for each other on a transaction advisory lock keyed by customer and request ID, so a retry finds the first join instead of failing the unit or per-customer checks against its reservation.
- **Units count when paid.** `Joins::commitAuthorized()` moves a join's units from reserved to committed once its hold is authorized, confirms the deal the first time the target is reached, records a price change when a tier boundary is crossed, and starts closing when the maximum is reached. Counting the same join again is a no-op. A payment that completes while closing is still at `settling_joins` counts (and never starts closing a second time, even if it fills the campaign); a later one, or one whose reservation already expired, is released and its hold voided.
- **Lock order**, everywhere: campaign, then participation, then payment.
- **Holds.** `Payments\Services\Holds::release()` runs inside the transaction that ends a join: a payment still waiting is marked failed, and an authorized one is voided after commit by the `VoidPayment` job. A void writes and commits its attempt row (key `void:{payment uuid}`), logs it, calls the provider outside any transaction, and records the result under the payment row lock. When the outcome is unknown the job retries, and asks the provider what happened before calling again.
- **Fake Moyasar.** Until the merchant account is approved (then `MOYASAR_DRIVER=moyasar`, see Integrations), `MOYASAR_DRIVER=fake` uses `FakeMoyasarGateway`, which reads the outcome from the provider payment ID (`fake_authorized_<payment uuid>` or `fake_declined_<payment uuid>`) and refuses to run in production. The join response carries the Moyasar form settings (`checkout`), with the callback at `{WEB_URL}/payments/return?payment_id=<uuid>`.
- **Payment statuses only move forward.** A failed payment row is never revived. When the provider payment it already tracks turns out to hold money after all (3-D Secure finished after the join ended), that hold is voided on the same row, `failed` → `voided`, and logged as `payments.orphan_hold`.
- **Live progress.** Every committed change to a campaign's units, price or status (`CampaignProgressChanged`, fired after commit) queues `BroadcastProgress`, which reads the numbers when it runs and sends them through Reverb (`apps/realtime`, a separate small app; see its README) as `progress.updated` on the public channel `campaigns.{uuid}`. One push waits per campaign at a time, so a burst of joins becomes one push, and runs for one campaign never overlap, so pushes leave in order. A push that waited behind other jobs still goes out, with the numbers of when it runs. Drafts are never sent, and clients cannot send anything on these channels (Reverb's client events are off). Pushes are best effort: a push Reverb does not take is logged (`campaigns.progress_push_failed`) and dropped. The website and app read `GET /campaigns/{id}/progress` (cached for 2 seconds as plain arrays, since a real cache store serializes what it keeps; a push stores what it sends there first, so a read made after a push is not older, short of a read that stalls for longer than the cache lasts) when they connect, poll it every 30 seconds while connected and every 5 seconds otherwise, and keep the payload with the higher `version`.
- **Campaign version.** `campaigns.version` grows by one with every UPDATE of the row, set by a PostgreSQL trigger (`campaigns_bump_version`), so no write path can forget it and row locks keep it in commit order. It is in every `CampaignProgress`; clients compare it rather than `updated_at`, which has whole seconds only.

## Payment confirmation (E9)

- **One path for every report.** The customer's return from the payment form (`POST /payments/{id}/sync`), Moyasar's webhook and the reservation expiry check all go through `Payments\Services\Confirmations`. It fetches the payment from the provider outside any transaction, never trusting the client or the webhook body, then applies it in one transaction in the lock order campaign, participation, payment.
- **What is accepted.** A hold counts only if it is `authorized` (not captured at once), for exactly the hold amount, in SAR, by card or Apple Pay on mada, Visa or Mastercard. Anything else is recorded with a `rejection_reason` and voided after commit, so money is never held untracked. A declined card leaves the reservation open, and `POST /me/participations/{id}/payments` starts another attempt while it lasts.
- **Statuses only move forward.** A payment row waiting for the customer follows the newest payment made through its form. Once a row is settled (declined, released with its join, or holding a hold), a hold under a new provider payment ID gets a row of its own, which is counted if the join can still use it and voided otherwise; a hold under the ID the failed row already tracks is voided on that row. A second hold for a join that already counts is `duplicate_hold`, even when its amount or card is also wrong; such rows never become the participation's `payment`. A join that already counts cannot start another payment (`409 already_paid`).
- **Before a reservation expires**, `campaigns:tick` asks the provider about payments it has started but not settled, so a hold that went through is counted rather than voided. A reservation that runs out after a declined or refused card ends as `payment_failed`, otherwise `reservation_expired`.
- **Webhooks** (`Payments\Services\MoyasarWebhooks`). Every event is stored in `payment_webhook_events` with its `secret_token` redacted. An event is verified by comparing that token with `MOYASAR_WEBHOOK_SECRET` (open question Q5 asks Moyasar whether a signature is offered). A verified event is processed once per event ID: a partial unique index covers verified rows only, so a forged event cannot take a real event's ID first. Processing is the queued `ProcessMoyasarWebhook` job (one at a time per event), which retries provider outages with backoff and records any other outcome on the event. An event whose tries ran out keeps `processed_at` empty: a resend from Moyasar queues it again, and so does `payments:requeue-webhooks` every five minutes for verified events still unprocessed after `webhook_requeue_after_minutes` and younger than a hold. Bodies over `webhook_max_bytes` are refused with 413 and not stored; NUL characters are stripped before storing.
- **Admin views.** `GET /admin/payments` filters by status and campaign, and `expiring_within_days` lists authorized holds soonest-expiring first. `GET /admin/payments/{id}` shows every provider call with its idempotency key.

## Closing and captures (E10)

- **The closing job** (`Campaign\Services\Closing`, queued as `CloseCampaign`, one at a time per campaign) does the step that is due under the campaign row lock and saves it in `closing_step`, so a re-run or a crash resumes safely:
  - `settling_joins` waits until no join is in flight (`reserved_qty = 0`), then writes once the final quantity, tier and price, each join's `capture_amount` (quantity × the lower of the final price and the price it held, plus any non-goods part of the hold), and `capture_by` (the earliest hold's capture cutoff). Below `min_target_qty` the campaign fails with `target_missed`.
  - `awaiting_supplier` waits for `POST /admin/campaigns/{id}/supplier-decision`, due `supplier_decision_lead_hours` before `capture_by`. Confirmed records the unit cost, stock and quotation reference and starts captures; fewer units than the final quantity is refused (`supplier_stock_short`); rejected, or no answer by the deadline, fails the campaign.
  - `capturing` queues one `CapturePayment` per authorized join. When none is left: nothing captured fails the campaign (`captures_failed`); below the target or the supplier's MOQ stops at `needs_admin` for `POST /admin/campaigns/{id}/below-target-decision`; otherwise the campaign moves to `purchasing` (`notifying`, then `done` once `CampaignSucceeded` is fired). The supplier purchase order (E12) is created in that transaction.
- **Wakeups, not polling.** The job is woken by what it waits for: `CampaignClosingStarted`, the last settling join (`Joins`), the supplier decision and the last capture result. `campaigns:sweep-closing` runs every five minutes as the backstop and fails campaigns past their supplier deadline.
- **Captures** (`Payments\Services\Captures`) follow the provider rules: write and commit the attempt (key `capture:{payment uuid}`), log it, call Moyasar outside any transaction, record the result under the campaign → participation → payment locks. On any error the payment is fetched first; a retry fetches before sending again, so a capture is never made twice. A declined capture, or a hold past its capture cutoff, leaves the join out (`capture_failed`) and voids the hold. An outcome still unknown after `capture_retry_hours` stays authorized and is logged critical for finance; it is never voided blind. Moyasar showing the payment captured for another amount (taken by hand in the dashboard, say) is never recorded as declined or voided: it is logged critical and left pending for finance, and the campaign waits at `capturing` until it is settled.
- **Failing** (`CampaignLifecycle::fail`) releases every join still holding units and voids their holds, before any capture only. Once money was taken, cancelling (from `capturing`, `needs_admin` or `purchasing`, or the below-target `cancel`) opens a `campaign_cancellation` approval request (202) for finance; it is carried out with refunds in E15.
- **Hold expiry.** `payments:expire-holds` (hourly) marks holds past `expires_at` as `expired`, after one last void attempt for any hold being voided. A hold whose capture was sent with an outcome still unknown never expires (logged critical as `payments.hold.expiry_blocked_by_capture`), since Moyasar may have taken the money. A live hold that expires is logged critical: the extension rule and the capture cutoff should make that impossible.
- **What customers see.** The final price and each join's capture amount are worked out at settling, but customers see them only once they are true: a join's `final_unit_price` and `capture_amount` once its hold is captured, and the campaign's `final_unit_price` once it has succeeded. Admins see the stored values throughout.
- **A pending cancellation request** does not stop the closing job: the campaign can still move to `purchasing` (or fail) while finance looks at it. Whoever carries the request out (E15) must re-read the campaign under its lock and act on its current state, not on the request's snapshot. Once approved, it does stop the campaign (E15, below).

## Orders, invoices and refunds (E11)

- **One order per captured join**, made in the transaction that records the capture (`Orders\Services\Orders::createForCapture`, called by `Captures`). It is idempotent per participation, so a re-run never makes a second order. The unit price is the campaign's final price and the goods total is unit price × quantity; whatever else was captured is the delivery fee. The database checks the sums (`goods = unit × qty`, `total = goods + fee`). Order numbers are `ORD-{yymm in Riyadh}-NNNNNN` from a sequence. Orders start `confirmed`; E12 and E13 move them on.
- **A simplified tax invoice** is issued with the order (`Orders\Services\Invoices`). Prices include VAT: each line is split with `Money::splitVatInclusive`, and the invoice totals are the sums of the lines. The seller's legal name, VAT and CR numbers and address come from `groupbuy.seller` (`GROUPBUY_SELLER_*`) and are copied onto the invoice (in production nothing is captured while they are the placeholders, because issued invoices cannot be changed), which carries the ZATCA phase 1 QR code (`Orders\Support\ZatcaQr`: seller, VAT number, time, total and VAT as base64 TLV). Invoice numbers are `INV-{year}-NNNNNN`, credit notes `CRN-…`. Once issued, a trigger refuses any change to the number, amounts, lines or seller, and any delete (SQLSTATE 23001); only the ZATCA reporting status and the stored file keys can change.
- **Invoice PDFs.** Every invoice and credit note gets an Arabic and English PDF with the QR code (`Orders\Documents\InvoicePdf`, mPDF, template `resources/views/documents/invoice.blade.php`). It prints only what the row holds (seller snapshot, lines, totals), so a file rendered later shows the same invoice. `RenderInvoicePdf` runs after the commit that issued it, never inside the money transaction, and writes `invoices/{year}/{number}.pdf` on the private documents disk before pointing `pdf_s3_key` at it, so a second run writes the same file to the same place. `invoices:render-pdfs` (every ten minutes) queues again any invoice still without its PDF `invoices.pdf_requeue_after_minutes` after issue: a job that ran out of tries is picked up at the next sweep, a lost one once its 30-minute unique lock expires (a copy is dropped while the first still holds it). Only invoices from the last `invoices.pdf_requeue_within_days` (7) are queued on their own; older ones keep failing for a reason someone must fix, so the sweep logs `invoices.pdf_missing` with their count and `invoices:render-pdfs --all` queues them afterwards. The folder year is the year in the invoice number (Riyadh time). `pdf_url` is a 30-minute signed link, null only between issue and the render. The XML and phase 2 reporting to ZATCA come with the e-invoicing integration, so `zatca_status` stays `pending` until then.
- **Customers** list and open their own joins (`/me/participations`) and orders (`/me/orders`); anyone else's is 404. A customer can cancel a join (`POST /me/participations/{id}/cancel`) only while the campaign is active, its deadline has not passed (even if the tick has not closed it yet) and the deal is not confirmed (proposed rule, Q16). A join still waiting for payment frees its reservation; a paid one gives its units back, voids its hold after commit, and records a price change if the next joiner's tier moves. Otherwise the answer is `409 cancellation_not_allowed`.
- **Operations** find orders by status, campaign, order number or the customer's phone as they type it (`GET /admin/orders`).
- **Refund requests** (`Payments\Services\Refunds`, `POST /admin/refunds`) lock the payment and refuse more than was captured less what is refunded or already asked for (`refund_exceeds_captured`). A full refund within `void_after_capture_minutes` of the capture is a `void`, anything else a `refund`. Each request gets its idempotency key (`refund:{uuid}`) when it is written and waits as `pending_approval` with a `manual_refund` approval request: support can ask, finance decides. Approving it, sending it to Moyasar and issuing the credit note are E15 (below).

## Supplier purchase orders (E12)

- **One per successful campaign**, created by the closing job in the transaction that moves the campaign to `purchasing` (`Orders\Services\PurchaseOrders::createForCampaign`), whether captures reached the target or an admin chose to proceed below it. A unique `campaign_id` makes a second one impossible. Its lines are the captured units of each variant, at the unit cost and currency the supplier reconfirmed. PO numbers are `PO-{yymm in Riyadh}-NNNN` from a sequence.
- **Money.** The total is in the supplier's currency. Its SAR value (`total_halalas`, for the ledger) is the total at `fx_rate_to_sar`, converted with `Money::convertTo` (exact decimal rate, integer arithmetic, half away from zero). The rate is the quote's when the order is in the quote's currency and 1 for SAR; otherwise it stays null until an admin records it. Changing the currency needs the total in the new currency and drops a rate that no longer applies; a SAR order's rate is always 1. Each line keeps its own currency, the one the supplier reconfirmed, so its unit cost never changes meaning.
- **Moving forward.** `PATCH /admin/purchase-orders/{id}` records the Alibaba order number, total, currency, rate and freight. `POST .../status` moves the order to `placed`, `supplier_confirmed`, `paid` or `shipped`; steps may be skipped, never undone, and only while the campaign is `purchasing`. Past `draft` the order needs its Alibaba order number and a SAR value, and once shipped a freight tracking reference (`purchase_order_incomplete`; CHECK constraints back this up). Leaving `draft` moves the campaign's confirmed customer orders to `processing`; `shipped` moves the campaign to `fulfilling` (a `supplier_shipped` campaign event). Lock order: campaign, purchase order, customer orders. Every step writes a status history row (with the admin's note) and an audit entry. Step dates (`occurred_at`) never go backwards (`step_date_out_of_order`), and the payment date can be recorded or corrected by PATCH once the order is paid.
- **Documents.** The Alibaba invoice, payment receipts, shipping and customs papers are kept with the order (`POST /admin/purchase-orders/{id}/documents`, at most `media.documents_per_purchase_order`), on the private documents disk and read through 30-minute signed links. A paper uploaded by mistake can be removed within `media.document_removal_hours` (24) of its upload; after that it is the record of what was ordered and paid and stays (409 `document_locked`). The file goes after the commit and both steps are audited.
- **Later.** `received` comes from the warehouse receipt (E13). `cancelled` comes with a campaign cancelled through finance (E15), which refunds every capture.

## Warehouse receipts and shipments (E13)

- **Receipt.** When the supplier's goods reach the pilot warehouse, `POST /admin/purchase-orders/{id}/receipts` counts them: received and damaged units for every variant of the purchase order, each exactly once (`receipt_lines_mismatch`). There is one receipt per purchase order, and only once it is `shipped`. The purchase order becomes `received`. Good units (received minus damaged) go to the campaign's `processing` customer orders, oldest first, and each order they fully cover becomes `ready_to_ship`. Orders left uncovered stay `processing` for an admin to refund (E15); the `goods_received` campaign event lists them with the missing and damaged counts. No stock or bin tables: the pilot is one warehouse and every unit is already sold. Lock order: campaign, purchase order, customer orders.
- **Shipment by hand.** `POST /admin/orders/{id}/shipment` hands a `ready_to_ship` order to the courier: the shipment starts `picked_up` and the order becomes `shipped`. One open shipment per order (a partial unique index); a parcel the courier brought back or a booking called off leaves room for another. Without a link, `tracking_url` comes from `couriers.tracking_urls` by courier name. Tracking updates entered by hand (`POST /admin/shipments/{id}/events`) may arrive out of order, so the newest one sets the shipment's status, and `delivered` and `returned` always do; none is dated before the pickup (`event_before_shipment`), so a mistyped delivery date cannot cut the return window short. `shipment_events` is append-only and says where each update came from. Each status the shipment takes writes a status history row. Lock order: campaign, customer order, shipment.
- **Courier API** (`Fulfillment\Couriers`, `COURIER_DRIVER`: `manual` until a courier is chosen, `fake` in development, `aramex`). `POST /admin/orders/{id}/shipment/booking` writes a `pending` shipment with `booking_status=requested` and a `booking_key`, commits, and `BookShipment` sends it after the commit (`CourierBookings`): mark `booking_sent_at` under the locks and commit, log and call the courier, then record the tracking number and label (PDF on the documents disk, `label_path`, before the row points at it). The courier documents no idempotency, so a booking that went out is never sent again on its own: a refusal or an unclear answer cancels the shipment with the reason in `booking_error` (with our reference, to look up in the courier's portal), and staff book again or ship by hand. `shipments:track` (every 30 minutes) first settles bookings left without an answer: queued again if they never went out `couriers.booking_requeue_after_minutes` after they were asked for, cancelled for checking if they went out more than `couriers.booking_answer_within_minutes` ago (longer than the booking job can run, so a slow answer is never thrown away). Each booking status writes its own status history row (`metadata.field = booking_status`). It then reads tracking for every parcel of the configured courier still on its way, least recently read first (`couriers.track_per_run`, `track_per_call` per call), with no transaction open, and records each new update once (`external_key`, a hash of the courier's update) through the same rules as updates by hand. `couriers.{driver}.codes` maps the courier's codes to statuses, `ignore` lists codes that are not movements (the booking itself), and any other code after the pickup means the parcel moved (`in_transit`); only a mapped code counts as the pickup, so a scan before it never tells the customer the order shipped. The first movement of a booked parcel sets `shipped_at` and makes the order `shipped`; the customer only sees a shipment once collected. A pending shipment can be called off (`POST /admin/shipments/{id}/cancel`), not while its booking waits for the answer (`booking_in_progress`). A full refund of a `ready_to_ship` order is refused while such a shipment is open (`shipment_open`); one booked between the request and finance's approval is called off when the refund closes the order (`Shipments::cancelForClosedOrder`): a booking not sent yet never goes out, one out with the courier is called off by its answer, and a booked parcel is logged (`courier.cancel_in_portal`) for staff to cancel in the courier's portal too. The courier gateway is resolved only when booking or tracking, so a courier set up wrongly never stops refunds or approvals. The Aramex driver follows Aramex's published JSON API (ClientInfo, CreateShipments with label report 9201, TrackShipments) and its update codes are only partly mapped: check both against the Aramex sandbox before launch.
- **Brought back.** `returned` (the courier could not deliver and brought the parcel back) puts the order back to `ready_to_ship`, for a new shipment or a refund, and the customer is told (`delivery_failed`). An order refunded in full while on its way is `cancelled` instead (`returned_after_refund`).
- **Delivery and completion.** Delivery marks the order `delivered` and starts its return window (`groupbuy.orders.return_window_days`). The hourly `orders:complete-delivered` command completes orders whose window has ended. The campaign becomes `completed` (a `completed` campaign event) once none of its orders is outside `delivered`, `completed`, `cancelled` or `returned`; anything that cancels or returns an order must call `Shipments::completeCampaignIfSettled` with the campaign locked.
- **Receipt photos.** Photos of the goods as they arrived (`POST /admin/inbound-receipts/{id}/photos`) are evidence for damage and shortfalls: added, never removed, at most `media.photos_per_receipt`, private with signed links.
- **Customer returns** (`Orders\Services\Returns`). Customers ask support; staff record the return on a `delivered` order within its window (`POST /admin/orders/{id}/return`, `refunds.request`): one per order, the order becomes `return_requested` and is not completed when the window ends. Approving (`POST /admin/returns/{id}/approve`) asks for a refund of the amount given (reason `customer_return`), which waits for a second admin with the finance role like any refund; once it goes through, `ReturnSettlement` (called by `Refunds` under its locks) makes the order `returned` and the return `completed`, even if a fee was kept. A full refund of an order waiting on a return closes it the same way. Rejecting puts the order back to `delivered`, completed by the hourly sweep if its window has ended. A return whose refund finance rejected or that failed can be decided again. The customer is told either way (`return_accepted`, `return_declined`). Lock order: campaign, customer order, return.

## Notifications (E14)

- **What customers are told.** A paid join counted (`joined`), the deal confirmed, the deadline extended, a hold released (campaign failed or cancelled, the customer cancelled, or the capture failed), a late hold voided (`hold_voided`: the payment came through after the reservation ran out, the campaign closed or the customer cancelled), the final amount charged, the order shipped and delivered. The Arabic and English texts are in `lang/{ar,en}/notifications.php`; each has a push title and a body, which is also the SMS. Campaign news (deal confirmed, extended) goes once to each customer with a paid join; anything about money goes once per join or order. Admin alerts are not sent yet: admins see campaigns waiting on them in the portal. A join counted once the campaign is closing (it filled the campaign, or came in while closing settled its joins) gets `joined_closing` and `deal_confirmed_closing`, which promise no deadline; they share the dedupe key of the plain message, so a customer never gets both.
- **Queued in the transaction that makes the news.** Services call `Campaign\Services\CampaignNotices` or `Notifications\Services\Notifier::send` inside their transaction. It writes one `notifications` row per channel (SMS when the customer has a phone, push when they have registered the app) with the template, the customer's language and a payload, and dispatches `SendNotification` after commit. A rolled-back change sends nothing. Each row has a `dedupe_key` (template, subject and channel), inserted with `ON CONFLICT DO NOTHING`, so a re-run of a closing step or a retried job tells nobody twice.
- **Payload.** Names go in both languages (`{"ar": …, "en": …}`), amounts in halalas (keys ending `_halalas`) and times in UTC (keys ending `_at`). `Notifications\Services\Templates` renders them in the customer's language at send time, amounts in SAR and times in Riyadh time.
- **Sending** (`Notifications\Services\Deliveries`). Each try is counted and committed before the provider is called, never inside a transaction; the result is recorded after. A failed try is due again after 1, 5, 15 and 60 minutes (`groupbuy.notifications`); the fifth failure marks the message `failed`, and so does a fifth try that never reported back. `notifications:dispatch-due` runs every minute and sends what is due, including messages whose job was lost (still queued 10 minutes after they were written or after a try started). So a message is never silently dropped, though a worker dying mid-send can rarely send it twice. Every send, retry and failure is logged without the phone number.
- **Push.** The mobile app registers its Expo push token (`POST /me/device-tokens`); a token belongs to the account that registered it last, and each customer keeps their 10 most recently seen devices. Tokens are stored with a SHA-256 hash for the unique index, and with the sign-in token that registered them, so signing out removes the device's token. `PushSender` sends through Expo (`expo` driver, see Integrations below); the `log` driver refuses to run in production like the SMS one.
- **Not sent through here.** Sign-in codes go straight to `SmsSender` (E5), because the customer is waiting and the code must never be stored. Email and in-app messages exist in the table but nothing sends them yet.

## Finance: approvals, refunds, ledger and reconciliation (E15)

- **A second admin decides.** Anything that moves money outside the normal flow waits as an approval request (`Finance\Services\Approvals`). `GET /admin/approval-requests` lists them (pending by default); `POST .../approve` and `.../reject` decide them (`Finance\Services\Decisions`), locking the subject first and then the request. Deciding needs `approvals.decide` (finance only), and the requester never decides their own request (403 `same_admin`). `manual_refund`, `campaign_cancellation`, `manual_void` and `ledger_adjustment` can be decided; `manual_capture` answers 409, because a capture always runs in the closing flow, which issues the order and its tax invoice (a hold still counting for a campaign is captured or released by closing or cancelling the campaign). A request whose subject is not of its type's kind also answers 409. Each decision is audited (`approval.approve`, `approval.reject`) and written to the status history; a request that no longer needs a decision is withdrawn (`cancelled`, nobody's decision, `approval.withdraw`).
- **Sending a refund** (`Payments\Services\Refunds::execute`, from `ExecuteRefund` after commit). (1) Lock the payment and the refund, move it to `processing` and write or find its attempt row (`refund:{uuid}`), then commit. (2) Log the call and send it: a void while the whole payment can still be voided (`void_after_capture_minutes`), otherwise a refund; a void Moyasar refuses is sent again as a refund under `refund:{uuid}:refund`. (3) Record the answer under the campaign, participation, payment and order locks: the refunded amount and payment status, a credit note, the ledger posting, the `refunded` message and, once everything went back, the order cancelled (not yet shipped) or returned (delivered). An unknown outcome leaves the attempt pending; the retry asks Moyasar first and sends again only if nothing went back, so a payment's refunds go one at a time: one that finds another in flight stays `approved` and is sent when that one settles. Only one runner works on a refund at a time (a five-minute cache lock around each try), so a second copy of its job, queued once the first one's unique lock ran out, stops instead of sending too: Moyasar documents no idempotency for refunds. A refund Moyasar refuses becomes `failed` and its amount can be asked for again.
- **Nothing approved is forgotten.** `finance:requeue-approved` (every five minutes) queues again every refund left `approved` or `processing`, and every approved campaign cancellation not yet carried out (`approval_requests.executed_at`), once nothing changed on it for `finance.requeue_after_minutes`: its job ran out of tries while Moyasar was down (picked up at the next sweep), or was lost (picked up once its lock expires: 4 hours for a refund, 3 for a cancellation, from dispatch). Both jobs are unique with a lock longer than all their tries, so a copy is dropped while the first still waits, and running one twice is safe (a refund asks Moyasar first; a cancellation does nothing once carried out). PostgreSQL, not the queue, remembers what is still owed.
- **Releasing a stuck hold** (`Payments\Services\ManualVoids`). For a hold Moyasar still keeps although it no longer counts here (reconciliation's `orphan_hold` and `stuck_void`): our payment is `failed`, `capture_failed` or `expired`, `voided` with an open `stuck_void` mismatch, or `authorized` with a rejection reason; no capture is under way, and no release approved earlier is still to run (`AdminPayment.void_requestable`). `POST /admin/payments/{id}/void` (`payments.void`, with a reason) opens a `manual_void` request on the payment; approving checks again under the payment lock and queues `ExecuteManualVoid` after the commit. Each try writes or finds the attempt row `void:{payment uuid}:{approval uuid}`, asks Moyasar first, and calls void only while Moyasar shows the payment `authorized`: already voided is recorded as done, anything else (captured, say) as failed `not_voidable` with nothing sent, and a payment Moyasar does not know as failed `not_found` (never retried). Success makes the payment `voided` (status history `manual_void`), supersedes any automatic void still pending, marks the approval executed and is audited (`payment.manual_void`). `finance:requeue-approved` queues again an approved manual void not yet carried out.
- **Ledger adjustments** (`Finance\Services\LedgerAdjustments`). `POST /admin/ledger/adjustments` (`ledger.adjust`) takes either balanced lines (debits equal credits, 2 to 20 lines, `ledger_unbalanced` otherwise) or the ID of a posting to reverse, and opens a `ledger_adjustment` request; nothing is posted until finance approves it, and then it is posted in the decision's transaction (`adjustment:{uuid}` with the approval request's ID, or a `reversal` of the original's lines flipped). A posting is reversed at most once (`already_reversed`, also while a reversal waits; a unique index backs it), and reversals are not reversed. Two requests for the same posting queue on an advisory lock, never a row lock: production's app role cannot UPDATE the append-only ledger, and `SELECT ... FOR UPDATE` needs that privilege (`Tests\Concerns\RunsAsAppRole` runs a test with production's grants to catch this). Rejecting frees the posting to be asked for again. `GET /admin/ledger/accounts` gives each account's debits, credits and balance, `GET /admin/ledger/transactions?type=&account=` the postings with their lines, `GET /admin/ledger/adjustments?status=` the requests (all `ledger.view`, finance and super admin).
- **Moyasar settlements** (`Finance\Services\Settlements`). `payments:settlements` (04:00 Riyadh time) reads every page of Moyasar's settlements (up to 50) and imports each one it has not seen with all its lines in one transaction: lines are matched to our payments by Moyasar's payment ID (`unmatched_count` counts the others, logged as a warning), and one `settlement` posting debits the bank with the net, payment fees with the fee less its VAT and recoverable input VAT with the VAT, and credits Moyasar clearing with the gross. A settlement with nothing in it is kept without a posting. One whose lines cannot be read is skipped and logged, the run fails so it is noticed, and the next run tries it again; older settlements are never held back behind it. `moyasar_settlements` and their lines are append-only. Finance reads them at `GET /admin/settlements` and `.../{id}/lines`. The settlement API is read as Moyasar documents it, and the amounts come from the lines: check both against the sandbox before launch.
- **Credit notes** (`Orders\Services\Invoices::issueCreditNote`). A first refund of the whole invoice copies its lines; anything else is one "Refund on order" line split at the invoice's VAT rate, then kept within the VAT and net still left on the invoice, so the notes never credit more VAT than was charged and the note that completes the refunds takes exactly what is left.
- **Cancelling after capture** (`Campaign\Services\CampaignCancellations`, from `ExecuteCampaignCancellation`). Approval is refused (409) once the campaign is fulfilling or ended. From approval until it is carried out the campaign waits: no capture is sent (`Captures` checks under the campaign lock; a capture whose outcome was unknown is settled by asking Moyasar and never sent again), asking to cancel again returns the approved request, closing does not move on and customers are not told the deal succeeded, the below-target decision and the purchase order answer 409. The job waits while a capture already in flight settles, then in one transaction: refunds of captured joins still `pending_approval` are rejected and their requests withdrawn (otherwise rejecting one later would leave that money with us), an approved refund of everything left for each captured join (sent after commit), its order cancelled, joins still holding a card released and voided, the purchase order cancelled (logged as critical if the supplier was already paid), the campaign `cancelled` with the counts in its event, and `executed_at` set. A campaign found unable to be cancelled then (only by a hand-made change) is logged critical and audited as `approval.not_carried_out`.
- **Ledger** (`Finance\Services\Ledger`). Double entry in SAR halalas, posted in the transaction that records the event. Capture: debit Moyasar clearing, credit customer prepayments (net) and output VAT. Delivery: the prepayment left after refunds becomes sales revenue. Refund: the reverse of its credit note, against revenue once it was recognised, otherwise against the prepayment, credit Moyasar clearing. A posting is unique per type and reference, so posting an event again returns the first. `ledger_transactions` and `ledger_entries` are append-only, a deferred trigger refuses a transaction whose debits and credits differ at commit, and a hand adjustment needs an approval request; mistakes are corrected by a reversal. Moyasar's settlements post the bank, fees and input VAT (below); supplier payments are not posted yet, and their account exists.
- **Reconciliation** (`Finance\Services\Reconciliation`). `payments:reconcile` runs at 03:00 Riyadh time for the day before (or `--date`): every payment that changed that day, and every one still open, is fetched from Moyasar and compared. Mismatches are `status`, `amount`, `missing_at_provider`, `orphan_hold` (we failed it, Moyasar holds money) and `stuck_void` (we released it, Moyasar still holds it, counting a hold still `authorized` with a rejection reason once `finance.void_grace_minutes` passed); a run that cannot reach Moyasar is `failed` with the error, any other error fails it with a pointer to the logs, and a run that has not moved for `finance.reconciliation_timeout_minutes` (it updates itself after every batch) is marked failed by the next one and keeps that verdict; the scheduler's overlap lock lasts as long, so a killed run never blocks the next day. Finance reads them at `GET /admin/reconciliation-runs` and `.../{id}/items?resolved=`, and closes one with a note (`POST /admin/reconciliation-items/{id}/resolve`); a fix that moves money goes through an approval request. Last, Moyasar's own list of the day's payments is read (`PaymentReports::payments`): one that holds or took money (`authorized`, `captured`, `paid`) and that no payment of ours points to is `missing_locally`, linked to our row when Moyasar's metadata names it (a confirmation that never arrived).
- **Audit log.** `GET /admin/audit-logs` (`audit.view`), newest first, filtered by subject (type and public ID), admin and action. Subjects without a public ID are shown by their row ID.

## Integrations

Each provider sits behind an interface with a fake or log driver for local work and tests, chosen in `.env` (`MOYASAR_DRIVER`, `SMS_DRIVER`, `PUSH_DRIVER`, `MEDIA_DISK`, `DOCUMENTS_DISK`). The fake and log drivers refuse to run in production.

- **Moyasar** (`Payments\Gateway\MoyasarGateway`, `MOYASAR_DRIVER=moyasar`). Basic auth with the secret key. The secret and publishable keys must be a live pair (`sk_live_`, `pk_live_`) in production and a test pair anywhere else. Moyasar names Mastercard `master`; it is stored as `mastercard`. Answers sort into three kinds: the payment in the state asked for is a success; 400, 404 or 422 is a refusal about this payment; anything else (timeout, 429, 5xx, and 401, 403 or 405, which are our own set-up) is an unknown outcome, which callers settle by fetching the payment before trying again. Moyasar documents no idempotency for capture, void or refund, so the attempt key goes as an `Idempotency-Key` header in case, but the fetch-first retries are what stop a double charge. Timeouts are in `services.moyasar`. On the website, Moyasar's own form (`moyasar-payment-form`) takes the card or Apple Pay, built from the API's `checkout` with the hold authorize-only; it records Moyasar's payment ID through `sync` before any 3-D Secure step, so a customer who never returns is still settled by the expiry check and the webhook. The mobile app shows the same form, from the website's `/payments/app` page in a WebView: the page tells the app Moyasar's ID, the app catches the return to `callback_url` and syncs with its own token.
- **SMS** (`SMS_DRIVER=unifonic` or `taqnyat`). Unifonic is the default: our reference (`otp:<uuid>`, `notification:<uuid>`) goes as the `CorrelationID`, so a retry of a message Unifonic already took is refused as a duplicate (409 or `ER-09`) and counts as sent. Taqnyat keeps no reference of ours, so a send whose answer was lost (a timeout after connecting, or a 5xx) is marked failed with `outcome_unknown` and never sent again; only a send that never reached Taqnyat, or that it refused, is retried. Both need an approved sender name (`SMS_SENDER`). Confirm the duplicate behaviour in Unifonic's sandbox before launch.
- **Push** (`Notifications\Push\ExpoPushSender`, `PUSH_DRIVER=expo`). Expo's push service, which delivers through Firebase and APNs with the credentials uploaded to EAS. Only Expo push tokens are sent; a token Expo reports as `DeviceNotRegistered` is deleted, and a send counts as delivered when any device took it. If a customer's devices belong to two Expo projects (after the app moves to a new EAS project), Expo refuses the batch and each project's devices are sent separately. Error messages carry Expo's codes, never the push tokens. `EXPO_ACCESS_TOKEN` only if enhanced push security is on. The mobile app must register `getExpoPushTokenAsync()` tokens with its EAS project ID, and Android builds need the Firebase project's `google-services.json` (see `apps/mobile/README.md`).
- **Files** (`MEDIA_DISK=s3-media`, `DOCUMENTS_DISK=s3-documents`). Product photos in a bucket that allows public reads by bucket policy (or a CDN, `AWS_MEDIA_URL`), never per-object ACLs. Supplier quote files, purchase order papers, warehouse receipt photos and invoice PDFs in a private bucket, read through signed links (`media.attachment_url_minutes`). Both disks throw on a failed write. Any S3-compatible store works with `AWS_ENDPOINT`; a blank `AWS_MEDIA_URL` or `AWS_ENDPOINT` means the bucket's own URL and AWS. Uploads go through `Support\Files\StoredFiles::storeThen` (file first, then the row, the file removed if the row is never written). Removing a file nothing refers to any more never fails the request: a failure is reported and logged as `storage.orphan_file`. Receipt photos and invoice PDFs keep their path without the disk, so `DOCUMENTS_DISK` stays the same once files are kept; moving to another bucket means copying the files across.
- **Errors** (Sentry, `SENTRY_LARAVEL_DSN`). Unexpected exceptions are reported through `Integration::handles()` in `bootstrap/app.php`; expected ones (`ApiException`, validation, 401, 403, 404, 429) never are. Request bodies, cookies and IPs are never sent (`max_request_body_size` is `never`, `send_default_pii` is off), since bodies carry phone numbers, sign-in codes and addresses. Query errors show the SQL with `?` placeholders (`mask_bindings_in_exception_messages` on the pgsql connection), and `Support\SentryScrubber` (`before_send`, `before_send_transaction`) removes PostgreSQL's DETAIL and CONTEXT lines, Saudi mobile numbers, query strings and function arguments from everything that goes.

## Conventions

- **Money:** columns end in `_halalas` (or `_minor` for supplier currencies) and are `bigint`. Customer prices include 15% VAT.
- **Time:** `timestamptz` columns in UTC, and the database session time zone is pinned to UTC in `config/database.php`. Convert to `Asia/Riyadh` only for display.
- **Client IP:** set `TRUSTED_PROXIES` to the load balancer's addresses in each deployed environment, or audit logs record the balancer's IP instead of the customer's.
- **Language:** API messages follow `Accept-Language`, Arabic by default. Customer-facing text columns come in `_ar` and `_en` pairs. Models live in their module and are stored in polymorphic columns by short names (`user`, `admin_user`, …) from the morph map in `AppServiceProvider`; add new models there.
- **Statuses:** a `varchar` column with a CHECK constraint, mirrored by a PHP enum. Each change writes a `status_transitions` row.
- **History is append-only:** a trigger rejects UPDATE, DELETE and TRUNCATE on history tables. The trigger stops mistakes from the app or a console session, not the table owner, who can drop it. In production, migrations run as an owner role and the app runs as a separate role with only SELECT and INSERT on history tables (plus USAGE on their sequences). The grants are the real boundary.
- **Business numbers live in `config/groupbuy.php`:** campaign length, hold lifetime, capture cutoff, minimum margin. Each one cites the decision behind it.
- **Request IDs:** every response has an `X-Request-Id` header. The ID appears in logs, audit records and status history.

## Testing

- Tests run against PostgreSQL, not SQLite, because triggers, `jsonb` and row locks behave differently.
- Concurrency rules (for example, many joins racing for the last 10 units) get tests that run real parallel transactions in forked processes, each with its own connection. They need the `pcntl` extension and commit their data, so the next test rebuilds the schema.
- CI lints the contract with Redocly and runs Pint and the full test suite on every pull request.
